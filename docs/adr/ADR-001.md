# ADR-001: Capas simples para persistencia; el seam de notificacion ya cubre el proximo cambio conocido

## Estado: Aceptado — 2026-11-15

## Contexto

Tras integrar Chain of Responsibility (validacion), Strategy (calculo por categoria) y Observer (notificacion) en el sistema de solicitudes de reembolso, corresponde decidir si el proyecto debe migrar a arquitectura Hexagonal completa (puertos e interfaces intermedias para persistencia y notificacion) o mantenerse en capas simples.

Datos del propio proyecto: una sola dependencia de persistencia (`RepositorioSolicitudesJpa`, con un unico metodo derivado), tres observadores conocidos en tiempo de compilacion y ningun plan de cambiar el motor de base de datos. Contabilidad si anuncio que, el proximo trimestre, integrara una API externa para el pago de las solicitudes aprobadas.

## Decision

1. **Persistencia: capas simples.** `SolicitudReembolsoService` sigue dependiendo directamente de `RepositorioSolicitudesJpa`, sin una interfaz de puerto intermedia ni mapper entre dominio y entidad. Un puerto de persistencia hoy seria una abstraccion especulativa (YAGNI) sin ningun caso de uso que lo requiera.
2. **Notificacion: sin cambios.** `ObservadorCambioEstado` ya es el seam necesario: `NotificadorContabilidad` puede reemplazar su implementacion interna por una llamada a la API externa el proximo trimestre sin modificar `SolicitudReembolsoService` ni los demas observadores.

La respuesta es distinta para cada concern porque el criterio de la Guia (sobrevivir 3 anos o mas con cambios de infraestructura) se cumple para la notificacion, donde hay un cambio concreto y fechado, y no para la persistencia, donde no hay ninguno previsto.

## Alternativas consideradas

- Hexagonal completo: puerto `RepositorioSolicitudes`, adaptador JPA y mapper entre entidad y dominio.
- Puerto de salida para notificaciones, adicional a `ObservadorCambioEstado`.

## Consecuencias

Positivas:
- No se agregan interfaces ni mappers de persistencia sin un caso de uso real que los justifique.
- El unico cambio de infraestructura con fecha conocida (integracion de Contabilidad) ya tiene su punto de extension listo.

Negativas:
- Si en el futuro se necesita cambiar de motor de base de datos, el puerto de persistencia debera introducirse retroactivamente; se acepta esa deuda tecnica de forma consciente.
- Al no haber mapper ni entidad JPA separada, la clase de dominio `SolicitudReembolso` lleva anotaciones `jakarta.persistence`; el dominio no importa Spring, pero si comparte clase con la persistencia. Las reglas ArchUnit garantizan que `procesamiento` no dependa de la persistencia.
- Un revisor que espere simetria total (puertos en todas las dependencias externas) puede interpretar la asimetria como inconsistencia si no lee este ADR.
